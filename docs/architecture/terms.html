STV4 Terms

Every right in the paper agreement represented as a typed, signed, hash-anchored term that the token enforces, executes, attests or discloses – so that an agent reads the substance, executes within a mandate, and an auditor rebuilds performance from logs. The gap that matters: the STBX holder is not a party to any signed document in the vault, so today there is nothing to anchor.

ENFORCED · the code refuses or permits EXECUTED · the code performs ATTESTED · hash + signatures on chain, performance off chain DISCLOSED · machine-readable text only Conflict in the paper

Hub: STV4 · siblings: Identity · Offering · Intelligence

1 · From clause to code

How a right travels

A clause is extracted into a typed term with its source reference, the terms are hashed into one root that both parties sign, the root is anchored on the instrument's passport, and each enforceable or executable term is bound to a Factory rule or facet parameter. Reading goes the other way: an agent fetches the JSON, recomputes the root, checks the signatures against the chain, and only then treats the terms as the agreement.

3 · The Terms model

One typed term per right, one root per instrument

Concerto-style schema serialised as JSON-LD: text, data model and logic bound through one model, as the Accord Project does, and hashed the way Ricardian contracts did in 2000 – the signed document's hash is the identifier every transaction carries. Documents are registered ERC-1643-style (name, uri, hash). The root lands on the passport, not on a new facet: the passport already owns snapshot roots, attestations and termsHash, and the question "who may anchor" is settled there.

InstrumentTerms {
  termsId:      bytes32            // keccak(instrumentId ‖ version)
  instrumentId: bytes32            // passport id · DTI / ISIN when they exist · issuer LEI
  version:      uint32, supersedes: termsId?
  documents:    [{ docId, role: SPA|SHA|Articles|Bylaws|DoA|Resolution, sha256, uri, signedBy[], envelopeId }]
  parties:      [{ role, legalName, lei?, subjectId, signerAddress }]
  terms:        [ Term ]
  precedence:   "code" | "text" | "term-by-term"
  signatures:   { issuer: EIP-712 over termsRoot, counterparty: EIP-712, attestor?: EIP-712 }
}
Term {
  termId:   "lockup.primary", class: ENF | EXE | ATT | DIS,
  source:   { docId, clause: "SPA 5.1" },
  params:   { ... }                          // typed per termId
  binding:  { facet, function, args } | { rule, args } | { schedule } | null,
  waiver:   { threshold, signers[] },        // who may lift it
  oracle?:  { kind, attestor, dispute }
}

// on chain, on the passport
termsRoot = MerkleRoot( leaf_i = keccak(termId ‖ canonicalJSON(params) ‖ salt_i) )   // salted like passport leaves
docsRoot  = MerkleRoot( sha256(document_j) )
event TermsAnchored(instrumentId, termsRoot, docsRoot, version, issuerSig, counterpartySig)

// on the token
TermsFacet.termsRoot() view; TermsFacet.enforce(termId, params, proof) // a rule proves its parameters sit in the signed root

4 · Read by agents, executed within mandates

What "AI can enforce" means, and the clauses that make it binding

Reading

  • The MCP tool makes three calls: passport.termsRoot(instrumentId) from the chain; GET record/<instrumentId>/terms.json from the Intelligence record; locally recompute both roots and check the two EIP-712 signatures. Only a matching JSON counts as the agreement.
  • "Can subject X sell Y tokens today" is answered with the same code the chain runs: canTransfer and whyBlocked, plus lockupsOf. Not a PDF parse – typed terms with a back-reference to the clause.

Executing

  • AgentAuthority mandates gain scope = termId: an agent may execute dividend.pay up to N per epoch, and cannot execute a term that is not in the signed root nor exceed the amount. AgentActed + TermExecuted are the proof.
  • Today consume is called by nobody in src/; the mandate becomes real only when the payout, consent and Board contracts call it.

Legal meaning (UK Law Commission, 2021; counsel to confirm)

  • Existing contract law accommodates smart legal contracts without new statute. Code can be a term, or the way a natural-language obligation is performed; where it merely automates a term, the code is performance, not a term.
  • Courts read code through a "reasonable coder". The Commission recommends the parties themselves say which layer prevails on conflict and allocate the risk of bugs and oracles.
  • Wyoming W.S. 17-16-625 lets a corporation issue share certificates as certificate tokens on a ledger – the route by which STBX could one day rise from "economic interest through STEL" to a tokenised Class C certificate, where "right in the SPA = right in the token" becomes literal.

7 · Decisions

For Gene, and for Max

Gene

  1. Level of the token. Stay "economic interest through STEL" (Terms anchor STEL ↔ holder), or lift STBX to a Class C certificate token under W.S. 17-16-625 (the holder becomes a shareholder, and "exactly the rights in the SPA" becomes literal). Larger, but the only route without an intermediary.
  2. Default precedence for every Factory instrument: term-by-term (recommended) or code.
  3. Oracles for VWAP and FMV: whose attestor counts – Stobox, an independent, or both.
  4. Order: PayoutFacet before ROFR (money visible first), or ROFR first because the lock-up to 2028 makes it moot until then.
  5. Publicity of Terms: full JSON open, or as the passport does – roots on chain, values by tiered access.

Max

  1. Is there a signed STEL token governance framework or STBX issuance terms for holders? If not, what gives a holder the dividend right under SPA 4.1 today?
  2. Which ROFR period and drag threshold apply: SHA (7 + 7 BD; Founder Majority >50%) or Bylaws (30 + 30 days; 70% Common A)? Same for pre-emption (SHA 6.1) against Articles 4.5(a).
  3. Bylaws 5.3(e): 25% or 50%?
  4. Where are the Investor Rights Agreement with the anti-dilution formula (Articles 4.3) and the waterfall schedule (SHA 5.4(c))?
  5. Will he sign "code is performance" with Terms prevailing for ENF/EXE, or prefer "text prevails" with code as the manner of performance?
  6. Under Wyoming and BVI law, may deemed acceptance (SPA 7.6) be replaced by the holder's EIP-712 signature as an electronic signature (SPA 7.5)?
