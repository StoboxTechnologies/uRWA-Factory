STV4 Intelligence

The record is the source; the oracle attests facts from the record to the chain; the token carries eligibility and terms; agents act within mandates. Any client system plugs into the same intake as documents do, and every figure arrives with its source, tier and expiry. The gap that matters: AgentAuthority.consume is called by nothing in src/, so a mandate today is a promise, not a limit.

1 · The thesis

Where BlackRock draws a box, we keep a record

In every figure of "The Machine-Native Economy" there is a small box – eligibility flag, trusted agent, discovery API – where a machine must believe a fact about the world that the chain does not prove. That box is the record. Our flag is not a bit: it is the result of a chain – document → value candidate with tier, confidence and dates → human election → attestation → view on the token – and it carries a source, an expiry and a signature.

Three canon rules bound what may be said: proofs go on chain, never data; each field is a statement about the record, not about the world; an anchor proves nothing was rewritten, never that it is true. So "Intelligence contracts" are not contracts that know the truth – they are contracts where anyone can check who said what, when, and on which document.

2 · The pipeline

From a client's API to an agent's action

Left to right. Connectors are a second door into the same intake as documents: they produce value candidates, never elections. Elections become figures per period, figures become signed oracle records, records become views on the token. Agents read the views and the record, and act only through a mandate that the target contract checks.

3 · Enterprise intake

"We take your API systems, any of them" – with the tier the source deserves

Today the record has one door: documents (160 types, 886 of 899 datapoints reachable by document). Connectors are the second door into the same funnel and must not bypass rule 5.1 – "the threshold sorts, a human elects". A connector produces a value candidate with source_kind = integration, never an election. An integration never raises a tier above what its source earns: QuickBooks is T2, not an audit. That is the honest answer to "plug in any API": we plug in any, and every number arrives labelled with where it came from.

Normalisation into the record

  • Registry v13.1: 899 datapoints, five dimensions (Company → Project → Asset → Instrument → Offering), 109 groups. Routing by datapoint code is automatic; a connector's field → dp_code mapping is written once per connector.
  • A figure is per period, not per record (ADR-0024): twelve months of Xero revenue do not overwrite each other.
  • Level of a financial fact (ADR-0026): EBITDA from statements is a legal-entity fact (T4–T5); a project's EBITDA is an allocation, never above T1 without an allocation basis. A connector to an ERP may not write project EBITDA as a fact.
  • Provenance per fact already in the schema: document_id + locator, tier_held, confidence, as_of, valid_until, created_by, superseded_by; election with a rule and an event in the hash chain. For integrations add one field: evidenceHash of the raw API response.

Where PII never goes

  • Into the passport tree – never, even hashed: a passport hash is still a pseudonym.
  • Into the oracle – only roots and hashes; never names, documents, 409A figures or PII.
  • Into the model layer of Copilot – row values do not enter; only document bytes for reading.
  • Person-level facts live in the DID claim plane by subject. Identity documents do not enter Stobox at all – only the verification result.
4 · Attested figures

Freshness classes for the client contract

  • B · ≤7 days: NAV, cap table, covenants.

Ruled 25.09.2026: corporate.action is structured

Gene: "we need autonomous assets for real". So the channel carries structured fields, not only a hash, and the payout, consent and lockup facets execute from it under a mandate. The hash stays as the evidence of the resolution behind the record.

struct CorporateAction {
  uint16  code;         // DIVIDEND · COUPON · SPLIT · BUYBACK · RECORD_DATE · CONSENT · LOCKUP · RECOVERY
  bytes32 docHash;      // the signed resolution or notice
  uint64  recordDate;   // snapshot block time for pro-rata
  uint64  dueBy;        // e.g. declaration + 15 business days (SPA 4.2)
  address asset;        // USDC, or the token itself for an in-kind election
  uint256 amount;       // total, or per unit when perUnit is true
  bool    perUnit;
  bytes32 ref;          // termId the action performs, so TermExecuted can cite it
}

Execution rule: an action is executable only if its ref is a term in the signed termsRoot and the record is signed under the channel's attestation model (§4b). Everything else is read-only.

4b · Who signs an attested figure

Ruled 25.09.2026: the client signs, Stobox signs, and roles can be given to others

Gene's ruling replaces the either-or of "relay or Eqvista": every oracle channel carries a signer set and a threshold, set per instrument at creation and changed only by the issuer admin under the upgrade delay. The record is published only when the threshold of signatures over the same EIP-712 payload is met. This keeps "inform, never certify" for Stobox – our signature says the relay carried the client's figure faithfully, the client's signature says the figure is theirs, a third party's signature says they verified it.

Signer roleWho holds the keyWhat the signature assertsDefault
ISSUERthe client's KMS or Safe (for STBX: STEL)"this figure is ours, from source X, as of T"required on every channel
RELAYthe Stobox relay key"carried unchanged from the record; evidenceHash Y matches the raw source"required on every channel
ATTESTORa named third party: auditor, valuer, fund administrator, custodian, Eqvista"we verified this figure under our engagement"optional; required by the preset for nav.perUnit, reserve.attested, FMV and VWAP used by a term
REGULATEDa BD, transfer agent or licensed administrator"recorded in the regulated register"optional; required where a regime demands it (Reg A+ TA, EU DLT MI)

Contract shape

struct ChannelPolicy {
  bytes32   channel;
  address[] signers;      // per role, resolved through AttestorRegistry
  uint8     threshold;    // e.g. 2 of {ISSUER, RELAY}; 3 when an ATTESTOR is required
  uint32    maxAge;
  uint16    maxDeviationBps;
}
function publish(Record r, bytes[] sigs) // valid only when threshold distinct signer roles signed keccak(r)
  • AttestorRegistry (interface exists, code does not) holds each signer's keys with validity windows, so a signature is checked against the key that was valid at observedAt.
  • A signer can be a client's own oracle service: the same L1 model as identity – their key, their liability, our rail.
  • Events name every signer: RecordPublished(channel, sequence, valueHash, signers[]).

What it changes on the other pages

  • Terms: VWAP and FMV used by a term are valid only under a channel policy that requires an ATTESTOR – no dispute path is needed for a figure nobody outside the parties signed, because such a figure cannot exist.
  • Offering: a regime preset may require the REGULATED role on shares.outstanding and captable.root.
  • Hub gap register: G14 (AttestorRegistry) moves from "Terms · Phase 4" to Phase 1, because the oracle cannot ship without it.
  • Liability wording for the MSA: "attested by [ISSUER] and carried by the Stobox relay; verified by [ATTESTOR] where shown" – for Max.
5 · Agents and mandates

Who the agent is, what it may do, how it is stopped

Identity of an agent

  • A wallet bound to the principal's DID subject (access) plus attestations about the operator (trust): agent.operator – legal entity, jurisdiction, registration, uDID; agent.kya – the five Stobox Attest checks (entity exists, key control, responsible person, sanctions and adverse media, endpoint liveness). Never a score of the agent's work.
  • Spending and transfer bounds are not claims – they are the mandate: maxPerAction, maxPerEpoch, tokens[], counterparties[].
  • ERC-8004: Identity registry yes (discovery); Reputation optional and only with an Attest or payment proof behind it; Validation is where Stobox writes the KYA result. Reason: 3–15% of registered agents have a live endpoint and reputation is 259× cheaper to buy than the median payment it protects (vault note on the agentic economy).

Guardrails

  • Every action is a signed intent (EIP-712, as the DvP Instruction and the STBU voucher pattern), checked twice: AgentAuthority.check / consume (mandate) and the token's compliance pipeline (eligibility).
  • A human confirms above a threshold – the same pattern as the oracle's deviation guard and the Copilot ladder Observing → Proposing → Drafting → Acting-leashed: levels 1–3 read and prepare unsent intents; level 4 consumes within caps; above caps, the Safe.
  • Logs: AgentActed(mandateId, agent, principal, selector, amount), MandateGranted / Revoked, Settled, TransferRefused – an agent's action is never indistinguishable from a human's.
  • Mandates can never express mint, roles, cuts, freeze, seizure or pause, by construction.

6 · Machine access

From a brochure with search to a surface for a deal

Today the Stobox MCP has six tools – five read the knowledge graph, one starts a lead in the CRM – with a public tier (no auth, 20 per IP per day) and a partner tier (OAuth 2.1). Add three planes on the same strategy. Honest superiority, without "first": others answer what exists on chain; we answer what to do with your asset, with a tier and a document behind every fact, an eligibility simulation and an intent queue under a mandate.

7 · Enterprise-grade, and the product frame

What must be true, and where "Operate" sits

Must be true

  • Data residency: US region for the first cohort; an EU region chosen at signup; SCIM, residency and BYOK in Enterprise.
  • SOC 2 / ISO: Vanta bought, security owned by Vlad, SOC 2 Type II without a public date (internal target Q1 2027), ISO 27001 after Type I; ISO 42001 paused. The Vanta card in the services register reads ARCHIVED with no payments found – reconcile with the goal.
  • Audit trail: hash chain of record events with a nightly anchor; on chain, the auditor pack from eth_getLogs without an indexer.
  • SLAs: freshness classes A / B / C plus the 24-hour price-correction window in the terms.
  • Keys: all roles on Safe 2-of-3 with hardware signers; KMS for the relay and the DID writer; annual rotation; timelock on cuts.
  • Disclosure page per channel, updated with each schemaVersion.
  • Data-licensing clauses (MSA, DPA + SCCs, AI addendum): the client licenses Stobox to publish proofs, not data; the attested figure belongs to the client; the relay signature is ours – "attested by the Stobox relay from a client-supplied source, evidenceHash X" (liability question for Max); x402 data to third parties only under an explicit per-item grant; nothing trains a model.

Not a fourth product

Canon: Organize (Intelligence) → Raise (Raisable, by Raisable Inc.) → Tokenize (Compass = Issue · Price · Board). Intelligence is always-on; the others are episodic. "Operate" as a fourth step collides with Enterprise C2 ("governed operating loop", withdrawn from the price list, 50/50 with Raisable) and with Copilot ("a capability of Intelligence, never an SKU").

Recommendation. Operate = two capabilities inside existing products: mandates and oracle channels inside Compass, per instrument (channel = "published update" $99 / $890 a year / $2,990 a year capped per issuer – SKUs already exist); agent read and MCP over the record inside Intelligence (anchoring included, unmetered). Say "Organize → Raise → Tokenize, and let software operate it inside mandates" without a fourth column in the price list. No percentage of a raise, no bps of AUM (withdrawn 11.08). If a real "C2" request ever arrives, that becomes Operate – born from a request, not a slide.

8 · Roadmap and decisions

What ships with STV4, what follows

With STV4 (see the hub)

  • Phase 1: the Stobox Oracle with five channels, the relay, the Safe-confirm path, the Intelligence facet – the first Intelligence contracts in code.
  • Phase 2: the Board reads price.reference; TransferRefused logging.
  • Phase 3: external audit, STBX issuance.

After STV4

  • Phase 4: connectors (Eqvista as direct signer v2; Xero / QuickBooks → revenue.period; Plaid), instrument-specific channels (NAV, covenant, occupancy), the Merkle payout for dividends (own contract, own audit).
  • Phase 5: AgentAuthority with principal = bytes32 DID subject, contracts that call consume, an agent SDK and a reference monitoring agent, the MCP "my deal" plane (record.read, action.propose), Attest phase 1 (KYA schema on EAS; deferred as K-129 today).
  • Phase 6: leash level 4 for agents, after a tamper-tested audit, as with Copilot.

Decisions for Gene

  1. corporate.action – ruled 25.09: structured fields an agent can act on (§4).
  2. Who signs an attested figure – ruled 25.09: the client signs, Stobox signs, and named third parties can be given signer roles per channel (§4b). Flexible by design.
  3. One registry on Base – ruled 25.09; every mandate by subject depends on it.
  4. Operate inside Compass and Intelligence, not a fourth product – confirm, so that the site and decks do not birth "Stobox Operate" before a mandate runs in production.
  5. Order C → B → A from the agentic-economy note (our own agent with an x402 service → paid calls → Attest as a product) and STBU's role – after Max; today all three hang as K-129 / K-130 / A-61.
