Stobox · internal architecture · v1.0 · 25 Sep 2026

STV4

The next Stobox security-token protocol: every STV3 facet rebuilt on the uRWA Factory on Base, four layers on top – identity, terms, offering, intelligence – and agents acting within mandates. This page is the hub; each layer has its own page. The one gap that matters: the Factory's rules read claims by subject, and Stobox DID cannot answer by subject – so every preset on Stobox DID refuses every transfer.

1 · The whole system

Everything STV4 depends on

Arrows point from what feeds to what uses it. The blue path is the one a transfer takes: identity claims written by the DID service, read by the token's compliance pipeline; signed records written by the oracle relay, read by the Intelligence facet and the Board. Arbitrum on the left is what exists today and gets snapshotted; nothing on Base is deployed yet except Stobox DID and EAS.

2 · One flow

A buy on the Board, from price to settlement

The Board never decides anything itself. It asks the oracle whether the reference price is fresh, asks the token whether the buyer may hold, then moves USDC and tokens in one transaction. The token's answer comes from the compliance pipeline: pause, trust, identity, frozen balance, rules – in that order.

Intelligence facet · what it reads

One function per channel, all views, all served from the Stobox Oracle's latest confirmed record for this instrument. The token never stores the value; it stores which oracle it trusts.

interface IIntelligenceFacet {
  function oracle() external view returns (address);
  function referencePrice() external view
      returns (uint256 usdc6, uint64 observedAt, bool stale);
  function valuation() external view
      returns (uint256 usd, uint64 observedAt, bool stale);
  function sharesOutstanding() external view
      returns (uint256 shares, uint64 observedAt);
  function capTableRoot() external view
      returns (bytes32 root, uint64 observedAt);
  function lastCorporateAction() external view
      returns (bytes32 docHash, uint16 code, uint64 observedAt);
}

4 · The four layers

One page per layer, statuses read from code

The Factory is the engine. Four layers give it identity, rights, a regulatory route and data. Each has its own page in this folder, in the same form as this one, with its own map, gaps and decisions.

1 · Identity

One subject-keyed registry of Stobox DIDs on Base with two read surfaces; salted hashes only; GDPR erasure by salt destruction; three levels for a client's own KYC; trust scoped per token.

Gap: rules cannot read claims from Stobox DID · Ruling 25.09: one registry

2 · Terms

38 clauses from the signed documents classed as enforced, executed, attested or disclosed; a typed Terms model anchored on the passport; seven clauses that make code the agreed performance.

Gap: the STBX holder is not a party to any signed document; passport, payout, consent and ROFR do not exist

3 · Offering

Regimes as first-class presets – Reg D, Reg S tranches, Reg CF, EU exemptions, UK, BVI – each bound to Factory parameters; the eight layers from issuer to reporting and the document on every arrow.

Gap: the regime field sets nothing; five verified defects in OfferingRegistry

4 · Intelligence

Client systems into the same intake as documents; figures per period into signed oracle channels; agents with DID identity acting within mandates; MCP as the machine surface; Operate inside Compass and Intelligence.

Gap: no contract calls AgentAuthority.consume

Safety rules

  • Fail closed on identity: no registry answer means no transfer. Fail soft on price: a stale record pauses only the company lot.
  • The relay key can post; only the Safe can confirm a deviation, pause a channel or rotate the key.
  • No EOA holds a token role after creation; the factory holds none either.
  • On chain: hashes, roots, validity, amounts. Never names, documents, 409A figures or PII.
  • Reference price is labelled as such in every event and NatSpec – it is not an offer price and not a market price.
  • Pause on Arbitrum before the snapshot; issue on Base only when Σ balances = totalSupply on both sides.

6 · Criteria

What "done" means, at four levels

Nothing moves to the next phase until every line of the level below is green. Acceptance is per module, delivery is per release, audit is per mainnet deployment, enterprise-grade is per year of operation.

Acceptance · per module

  • forge test green, forge fmt --check clean, branch coverage ≥ 80% on the module.
  • Every fix has a test that fails when the fix is reverted (repo rule, doc 34).
  • ERC-7943 conformance kit passes on the token with the facet installed.
  • Invariants hold under fuzzing: Σ balances = Σ subjectBalance = totalSupply; frozen ≤ balance; no forced op changes a cap.
  • Identity: a Reg S preset refuses a US subject and admits a non-US subject with three linked wallets counted as one holder.
  • Oracle: a record past maxAge reads stale; a > 15% step is not readable until confirmed; sequence never repeats.
  • Emergency: forced transfer works while paused, refuses an ineligible recipient, moves lockups, emits ForcedTransfer not Transfer.
  • python3 verify.py and --self-test green; docs 07 and 14 updated in the same commit.

Delivery · per release

  • Deploy script in script/ runs on Base Sepolia from CI with no manual step; addresses written to docs/deployments/.
  • Every contract verified on Basescan and Sourcify; bytecode matches the tagged commit.
  • All roles read back from chain and match the roles table: Safe holds them, no EOA does.
  • Build-log entry (doc 34) and handoff (doc 26) refreshed; work registry (doc 24) statuses match the code.
  • Runbooks exist for: price update, deviation confirm, key rotation, pause, forced transfer, migration claim support.
  • Auditor pack produced from the deploy block and checked against the chain: register, lockups, roles, oracle history.
  • For STBX: holder letter sent T−30, migration page live, support FAQ "STBX is not STBU" published.

Audit · per mainnet deployment

  • Internal adversarial audit (finders by subsystem, skeptics per finding) with every finding resolved or explicitly deferred with reason.
  • External audit of the whole scope: core + facets (≈ 4.8k lines) plus new modules (≈ 1–1.5k lines): IdentityRegistry, Oracle, IntelligenceFacet, EmergencyFacet, Board, MigrationClaim. Estimate $60–150k, 3–4 weeks plus re-check.
  • Code frozen at a tagged commit for the audit; any change after the freeze goes back to the auditor.
  • All high and critical findings fixed and re-tested; mediums fixed or accepted in writing by Gene.
  • Report published in the repo with the tag it covers; the explorer audit tag set.
  • Public audit contest (OP-05) optional after the external report, never instead of it.

Enterprise-grade · per year

  • Keys: all roles on Safe 2-of-3 or better with hardware signers; KMS for the relay and the DID writer; documented rotation, tested once a year.
  • Timelock on upgrades; every cut announced with a diff before it executes.
  • Monitoring: alerts on stale oracle, failed relay run, role change, pause, forced operation, registry drift between chains (reconciler).
  • Incident runbook with owners and a 24-hour price-correction window written into the terms.
  • Reconciliation: on-chain register ↔ SPV register ↔ cap table, monthly, signed by the CFO.
  • Availability: the token never depends on the indexer; the auditor pack rebuilds from eth_getLogs alone.
  • Insider policy: blackout windows and pre-clearance for company, founder and ≥ 5% wallets listing on the Board.
  • Disclosure page for the methodology of every oracle channel, updated with each schema version.
7 · Build order

Foundation first, then identity and data, then the market

The order is set by dependencies, not by size: nothing on Base can be issued as a Reg S instrument until the registry serves claims by subject, and nothing holding money ships before the external audit. Estimates assume two Solidity engineers, one full-stack engineer and part-time DevOps.

Phase 0 · 3 weeks
Foundation: G2–G10, G16, G17 closed with failing-first tests
  • OfferingRegistry: operator role on the token, treasury = token treasury, aggregate limits by subject, no removeRule after activation, no settle from Active, bounded forceStatus, single PurchaseRecorded
  • Treasury: reserve on purchase, per-asset unlock
  • EmergencyFacet to the four STV3 defects as tests
  • resyncSubject; role admin split; setters under the upgrade delay
  • Interfaces reconciled with code; handoff and CLAUDE.md refreshed
Phase 1 · 4 weeks
Identity and data: the two things STV3 never had
  • IdentityRegistry on Base + DID service writing both chains with one KMS key; migrate 305 DID
  • StoboxOracle with five channels; relay job; Safe confirm path
  • IntelligenceFacet on the token
  • Base Sepolia deployment from CI; auditor pack v1
Phase 2 · 4 weeks
Market and migration: the STBX instrument
  • MigrationClaim (Merkle snapshot; STBU voucher pattern for signing)
  • CompassBoard with TransferRefused logging, ERC-1271, partial fills
  • Board page and indexer; migration page; holder letter draft
  • Internal adversarial audit of the whole scope
Phase 3 · 6–8 weeks
Audit and launch
  • Code freeze, external audit, fixes, re-check
  • Pause STBX on Arbitrum, snapshot, publish hash
  • Issue 1,415,000 on Base, RegS preset, cap locked; recreate 6 lockups
  • Open claims, then the Board; company lot at the reference price

Critical path: Phase 0 → IdentityRegistry → external audit → issuance. The oracle and the Board can slip a week without moving the launch; the registry cannot. Total to mainnet: 17–19 weeks from start, Q1 2027 – after the Reg D round closes on 10.12.2026. Phases 4–6 (Terms facets, connectors, mandate-calling contracts, agents) follow on the layer pages.

8 · Decisions

Settled and open

Settled (Gene, 25.09.2026 unless noted)

  1. STV4 is the uRWA Factory, not a fork of STV3: STV3 facets are rebuilt, not copied.
  2. STBX: 1,415,000, 1 token = 1 Class C share via Stobox Tokenized Equities Ltd (BVI); moves to Base; reference price = Eqvista RTV; no US persons; Reg D perk removed.
  3. Compass Board in BVI, manual escrow lots, no fees, no treasury, operated by Stobox Innovations Ltd; a Compass function.
  4. KYC → DID → every Stobox product (10.09.2026); Stobox DID on Base deployed the same day.
  5. Attestations and anchoring come later (wave 4, 08.08.2026); Stobox Attest is a separate sub-project (R-168).
  6. Voucher pattern: EIP-712, KMS-signed, nonce-inherited – accepted in ADR 0002/0003/0005 for STBU and reused here.

Open

  1. One registry or two on Base (§4, option A assumes two for now).
  2. Who signs the oracle: relay now, Eqvista when there is an agreement and an API.
  3. Merkle claim or voucher for the STBX migration; both patterns exist, the spec says Merkle.
  4. The 24-month legal lockup to 01.04.2028: in code at issuance or on paper only – Max.
  5. Deactivated linker semantics before migration – Max and Vlad.
  6. Dividends: snapshot-and-Merkle contract, when and in which audit.
